# Module: pi-extension

## Purpose

Integrate macos-computer-use with the pi.dev Pi coding agent as a dedicated macOS automation front end. Users issue natural-language automation tasks in Pi's native TUI, and Pi calls bounded element-first tools backed by one task-scoped disposable Run.

## Dependencies

- Project: Public Client API and public Contracts only.
- External: `@earendil-works/pi-coding-agent` Extension API and Node child-process IPC.
- Forbidden: Kernel or Adapter imports, Tart/Appium/Mac2/native identifiers, absolute-coordinate actions, arbitrary Guest commands, Host shell/file-tool fallback, and direct VM lifecycle control.

## Public Interface

The Extension registers model-callable tools `macos_begin`, `macos_observe`, `macos_query`, `macos_expand`, `macos_action`, `macos_assert`, `macos_finish`, and `macos_abort`, plus `/macos-status` and `/macos-abort` commands. Tool inputs and results use strict public Contract schemas and logical references only.

Loading the Extension selects dedicated macOS-automation mode. Every agent turn receives only the `macos_*` tool set and explicit no-fallback instructions; prompt wording does not enable or disable that boundary. General coding or Host tasks require a Pi session where this Extension is not loaded. The `tool_call` guard rejects every non-`macos_*` tool while the Extension is loaded, including tools contributed later by other extensions.

`macos_begin` requires `application: { name }`, confirms the display name through Pi UI, and freezes it with required final assertions before creating the runner/VM. It rejects bundle IDs, paths, launch arguments, and window selectors. Observation, query, expand, action, and assertion calls are serialized through that Run. `pressKey` and `typeText` reject both a target query and immediate assertions. Pi focuses controls with a separate click; selects, clears, moves the caret, and submits with separate `pressKey` actions; and inserts text only with targetless `typeText`. Key-result verification uses a later `macos_assert` or the frozen final assertions. After each successful mutating action, the Extension obtains a fresh compact Observation through the same supervised runner and returns it alongside the ActionResult so both the model and user can inspect the resulting logical UI state. `macos_finish` confirms normal Tart destruction, then closes the task, waits for Evidence finalization and cleanup, and returns the complete RunResult and RunId. Refusing finish leaves the Run active. `macos_abort` cancels and waits for cleanup without confirmation. A second active task is rejected.

## Supervision And Fail-Dead Lifecycle

The Pi process does not directly own the active `client.run()` callback. It spawns one local MCU task-runner child process over private, versioned, strictly validated Node IPC. The runner owns Client, the Run handle, final assertions, operation serialization, Evidence finalization, and cleanup. Runner protocol types and process entry points are private package implementation paths.

Pi and the runner maintain a short monotonic lease through heartbeat messages. Pi serializes ordinary requests through one FIFO while heartbeats continue independently during slow operations and startup. Any of the following irrevocably revokes task authority: Pi process exit, IPC disconnect/EOF, Extension unload or failure, explicit abort, heartbeat expiry, malformed/out-of-order IPC, unknown action dispatch/outcome, or runner shutdown. On revocation the runner aborts the active Run before accepting another operation, rejects queued and future tool calls, and enters cleanup. A request that completes after revocation cannot report success.

The Extension handles session shutdown, command/tool failure, cancellation, and normal process signals idempotently. A terminal `macos_*` failure after begin revokes task authority and causes the Extension itself to request abort and wait for bounded runner finalization/cleanup before it returns the original structured failure; the model is not expected to issue `macos_abort` after that failure. Correctable pre-dispatch discovery failures (`TargetNotFound`, `TargetAmbiguous`, and `SnapshotIncomplete`) remain non-terminal but open an Extension-owned discovery-recovery gate. While the gate is open, model calls may observe, refine a query, or abort; action, expand, assert, and finish are rejected before IPC, while the operator-only status command remains available. A successful fresh observation or unique query closes the gate. Lease/readiness expiry, session/application/window/foreground loss, Provider failure or timeout, unknown dispatch/outcome, Evidence failure, protocol/supervision failure, and any post-dispatch action failure are terminal. Once such a terminal failure occurs, a turn-scoped latch blocks every later model-callable `macos_*` tool through the Pi tool-call guard before Extension execution or runner IPC; only a later user turn resets that latch. Shutdown waits at most 120 seconds for runner acknowledgement and Client finalization. At the deadline it terminates the runner and closes local authority; any durable ownership record remains for normal recovery before the next task. Abort during startup waits for the in-flight recovery/run-start lifecycle to settle or for the same deadline; it cannot acknowledge cleanup merely because Client Run creation has not started. No design claims cleanup can execute inside a process after `SIGKILL`. Pi may run on its supported Node version; the supervisor explicitly launches the MCU runner with supported Node 24 or fails before task creation with setup guidance.

The child environment contains only the minimum process variables needed to run Node and Tart plus secret names explicitly permitted by parsed GatewayConfig. It never inherits the complete Host environment or unrelated credentials. The child is not detached and receives no reusable endpoint or credential outside that allowlist.

## Confirmation And Tool Policy

Observation, query, expand, status, and deterministic assertion tools are read-only and require no confirmation. Beginning a task requires one confirmation naming the target application before any VM allocation. Ordinary `macos_action` calls execute without another confirmation. The action tool accepts an optional `confirm: true` flag used only when the user's current Prompt explicitly requests confirmation for that action; the Extension then displays exactly one action confirmation and denial prevents dispatch without ending the Run. Pi must call the tool directly and must not emit a separate natural-language confirmation request or pre-announcement. Normal `macos_finish` requires one confirmation before finalization destroys the Tart clone; denial leaves the Run active. Explicit abort, terminal failure, cancellation, Extension/session shutdown, IPC loss, and process signals perform fail-dead cleanup without confirmation. Begin and normal finish fail closed when interactive UI is unavailable; a flagged action also fails before dispatch without UI.

The task permits at most 100 model-callable `macos_*` operations after a successful begin, counting read and write operations but excluding internal heartbeats, Extension-owned final-assertion probes, and operator commands. A fourth consecutive equivalent action fails before dispatch. Crossing either limit revokes the task rather than allowing alternate tools.

## Data And State Flow

Pi receives compact snapshots by default. Compact element lines include stable accessibility identifiers when available, allowing direct logical queries without broad expand sweeps. Structured query and expand are requested only as needed. Pi may construct an element-targeted action only from locator fields and values actually present in the latest compact/expanded result or returned by a successful query; it must not invent placeholder-derived name/label/value fields, use empty-field guesses, or carry a stale failed query into an action. The runner still requires every element-targeted action query to resolve uniquely against the latest canonical Observation before dispatch. `typeText` has no target and relies on a separately evidenced prior click/focus sequence. A successful mutating tool result includes a fresh compact post-action Observation; screenshots are not returned by this Extension. After every successful action or explicit `macos_assert`, the Extension evaluates all frozen final assertions through existing supervised `assert` requests. Failed or unverifiable probes leave the task active and do not change the action result. A `typeText` action cannot make the task completion-ready solely because the focused input now matches a final value assertion; completion requires a later explicit `macos_assert` or subsequent successful action. When all eligible frozen assertions pass, the Extension marks the task completion-ready and includes that fact in the tool result; subsequent model-callable work is limited to `macos_finish` or `macos_abort`, while the operator-only status command remains available. Query, observe, expand, assert, and action calls—including extra exploration and double-click—are rejected before runner IPC. The Extension never returns resolved bundle IDs, Provider endpoints, native IDs, geometry, Artifact paths, Host or Guest paths, secrets, or raw diagnostics to the model. Remote webpage/UI content is untrusted task input; it cannot change dedicated tool restriction, frozen application, confirmations, final assertions, or completion verdict.

The private task protocol uses version 2. Version 1 is rejected rather than guessed. Its `begin` request carries ApplicationTarget plus final assertions, and its action request rejects both target and immediate assertions when the action is `pressKey` or `typeText`; `appendText` and `replaceText` are rejected as unknown action kinds. Confirmation intent is consumed by the Extension before IPC and does not enter the runner protocol. The protocol contains no ranking-model field or candidate-ranking operation. A future optional decision advisor may consume a separately specified sanitized Observation projection and finite legal candidate IDs, but cannot be an execution authority; v1 adds no Laya dependency, model, process, interface, or placeholder abstraction.

Expected Client and Run failures cross IPC as bounded structured errors preserving the stable Client error code and safe allowlisted provider category needed for terminal classification and diagnosis, and are returned to Pi as safe structured tool results. When an action was dispatched successfully but bounded after-Observation attempts fail, Pi receives the earliest safe normalized Provider cause retained across the Observation attempt/retry chain rather than a generic missing-state or later cascading error; Provider success remains separately recorded and is never converted to verification success. Protocol corruption, supervision loss, confirmation denial, cancellation, and terminal mutating-operation failure close task authority and trigger bounded cleanup; raw response bodies, stacks, paths, native IDs, user-entered text, secrets, and credentials are never projected to the model. Task completion is never inferred from model text.

## Internal Structure

- Pi Extension factory, exact TypeBox tool schemas, dedicated tool policy, confirmation, commands, and safe result rendering.
- Private strict IPC schemas with protocol version, task/request identity, monotonic sequence, bounded values, and correlated response types.
- Private task-runner session state machine, action materialization, Client lifecycle ownership, heartbeat lease, and safe projection.
- Private supervisor with independent heartbeat channel, caller FIFO, bounded shutdown, minimal child environment, and idempotent process termination.

## Architecture

- Architecture level: Level 2 integration Adapter/facade within the existing private package.
- Runtime boundary: Pi Extension process plus one supervised local Node child process.
- Dependency direction: Pi Extension and runner depend on Public Client/Contracts; Client/Kernel never import Pi.
- Package boundary: `./pi-extension` is the only Pi package export. Root `package.json` declares a standard local Pi package manifest pointing at the built Extension, so users install the repository directory with `pi install <path>` and subsequently launch plain `pi`; `--extension` remains a one-run development option. This private repository does not promise npm publication. Runner/session/protocol files are not package exports.

## Error Handling

Strict validation rejects unknown fields, unsupported versions, mismatched task/request identities, non-monotonic sequence, wrong response kinds, oversized values, and invalid actions before dispatch. Transport or protocol failure rejects all pending work and permanently closes that supervisor. Mutating cancellation races the in-flight request and cannot return a late success.

## Verification Scope

Deterministic tests cover official Pi API type compatibility, exact tool schemas including ApplicationTarget and optional action confirmation intent, dedicated tool restriction, target confirmation before allocation, normal-finish confirmation, protected/invalid target failures, protocol v2 validation, stable Client error preservation, safe structured errors, one-task ownership, FIFO execution with independent heartbeat, task-wide and repeated-action limits, default confirmation-free actions, explicitly flagged single confirmation, denial behavior, no duplicate natural-language confirmation instruction, compact post-action feedback, immediate removal of append/replace kinds, rejection of target/assertion-bearing `pressKey`/`typeText`, locator-provenance guidance, correctable discovery gating and recovery, Extension-owned frozen-final probes, typeText self-completion suppression, completion-ready suppression of extra query/assert/action/double-click calls, terminal-failure tool-call suppression and abort/cleanup without confirmation, same-turn restart rejection, cancellation, unknown outcome revocation, Node 24 runner selection, bounded startup/shutdown, environment allowlisting, final result mapping, disconnect, child failure, and no post-revocation dispatch.

A provisioned macOS profile drives the Pi Extension-style lifecycle against a disposable clone and confirms complete Evidence plus no residual managed VM after normal finish and after Pi-parent loss. A second provisioned case kills the runner, then proves the next startup performs recovery before accepting a new task. The Safari TodoMVC profile runs through the actual Extension tool facade, focuses the address bar, sends Command+A and Backspace as separate `pressKey` actions, sends the URL through targetless `typeText`, performs separate Enter navigation, focuses the web text field, sends Todo text through targetless `typeText` without newline, submits through one later untargeted assertion-free Enter, reaches completion-ready from the frozen final assertion, rejects a subsequent extra double-click before Provider dispatch, permits normal finish, proves every screenshot Artifact has display scope from `macos: screenshots`, proves no element-value write or window-element screenshot request occurs, and leaves no managed clone. Missing provider prerequisites are reported as skipped and do not satisfy this acceptance obligation.

## Current Invariants

- Natural-language planning remains owned by Pi; MCU remains the execution, verification, Evidence, and cleanup authority.
- Losing Pi/Extension/IPC supervision stops new automation dispatch immediately.
- Every active task has one runner, one Run, one lease, one caller FIFO, and an independent heartbeat channel.
- Expected failures remain structured; late, unknown, or revoked results never become success.
- A terminal tool failure permits no second Run in the same Pi agent turn.
- A correctable discovery failure permits no action until a fresh observation or unique refined query succeeds.
- Completion-ready permits no model exploration or mutation; only finish and abort remain model-callable, while the operator status command remains available.
- Required final assertions and RunResult, never Agent text, decide completion.
- Pi input deals only in the confirmed application display name; resolved bundle ID and path never enter model context.
